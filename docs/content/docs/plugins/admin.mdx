The Admin plugin provides a set of administrative functions for user management in your application. It allows administrators to perform various operations such as creating users, managing user roles, banning/unbanning users, impersonating users, and more.

## Installation

<Steps>
  <Step>
    ### Add the plugin to your auth config

    To use the Admin plugin, add it to your auth config.

    ```ts title="auth.ts"
    import { CinaAuth } from "cinaauth"
    import { admin } from "cinaauth/plugins" // [!code highlight]

    export const auth = CinaAuth({
        // ... other config options
        plugins: [
            admin() // [!code highlight]
        ]
    })
    ```
  </Step>

  <Step>
    ### Migrate the database

    Run the migration or generate the schema to add the necessary fields and tables to the database.

    <Tabs items={["migrate", "generate"]}>
      <Tab value="migrate">
        ```package-install
        npx auth migrate
        ```
      </Tab>

      <Tab value="generate">
        ```package-install
        npx auth generate
        ```
      </Tab>
    </Tabs>

    See the [Schema](#schema) section to add the fields manually.
  </Step>

  <Step>
    ### Add the client plugin

    Next, include the admin client plugin in your authentication client instance.

    ```ts title="auth-client.ts"
    import { createAuthClient } from "cinaauth/client"
    import { adminClient } from "cinaauth/client/plugins"  // [!code highlight]

    export const authClient = createAuthClient({
        plugins: [
            adminClient()  // [!code highlight]
        ]
    })
    ```
  </Step>
</Steps>

## Usage

Before performing any admin operations, the user must be authenticated with an admin account. An admin is any user assigned the `admin` role or any user whose ID is included in the `adminUserIds` option.

To create the first admin user, run the CLI after adding the Admin plugin and applying the schema:

```package-install title="Terminal"
npx auth@latest create-admin --email admin@example.com --name "Admin" --role admin
```

If users already exist, the CLI asks for confirmation before creating another admin. Use `--force` or `--yes` to skip that prompt. The CLI marks the admin email as verified by default; pass `--no-email-verified` to disable that.

  ```ts
    /**

     */
  ```

  ```ts
    /**
     * The offset to start from. 
     */
    offset?: string | number = 100
    /**
     * The field to sort by. 
     */

    /**

     * The field to filter by. 
     */

    /**
     * The value to filter by. 
     */
    filterValue?: string | number | boolean | string[] | number[] = "hello@example.com"
    /**
     * The operator to use for the filter.
     */
    filterOperator?: "eq" | "ne" | "lt" | "lte" | "gt" | "gte" | "in" | "not_in" | "contains" | "starts_with" | "ends_with" = "eq"
  }
  ```
</APIMethod>

#### Query Filtering

The `listUsers` function supports various filter operators including `eq`, `contains`, `starts_with`, and `ends_with`.

#### Pagination

The `listUsers` function supports pagination by returning metadata alongside the user list. The response includes the following fields:

```ts
{
  users: User[],   // Array of returned users
  total: number,   // Total number of users after filters and search queries
  limit: number | undefined,   // The limit provided in the query
  offset: number | undefined   // The offset provided in the query
}
```

##### How to Implement Pagination

To paginate results, use the `total`, `limit`, and `offset` values to calculate:

* **Total pages:** `Math.ceil(total / limit)`
* **Current page:** `(offset / limit) + 1`
* **Next page offset:** `Math.min(offset + limit, (total - 1))` – The value to use as `offset` for the next page, ensuring it does not exceed the total number of pages.
* **Previous page offset:** `Math.max(0, offset - limit)` – The value to use as `offset` for the previous page (ensuring it doesn’t go below zero).

##### Example Usage

Fetching the second page with 10 users per page:

```ts
import { authClient } from "@/lib/auth-client";

const pageSize = 10;
const currentPage = 2;

const users = await authClient.admin.listUsers({
    query: {
        limit: pageSize,
        offset: (currentPage - 1) * pageSize
    }
});

const totalUsers = users.total;
const totalPages = Math.ceil(totalUsers / pageSize)
```

### Impersonate User

This feature allows an admin to create a session that mimics the specified user. The session will remain active until either the browser session ends or it reaches 1 hour. You can change this duration by setting the `impersonationSessionDuration` option.

<APIMethod path="/admin/impersonate-user" method="POST" requireSession>

By default, admins cannot impersonate other admin users. To allow this, grant the `impersonate-admins` permission to a role:

```ts title="auth.ts"
const superAdmin = ac.newRole({

  user: ["impersonate-admins", ...adminAc.statements.user],
```

</Callout>

## Stats, Wallet & Passkey Endpoints (CinaSeek Admin)

The admin plugin additionally exposes read/aggregation endpoints for the
CinaSeek Admin dashboard, plus SIWE wallet and target-user passkey management.
All operations are authorized through explicit resource permissions.

### Stats Overview

**Server:** `auth.api.statsOverview({ headers })`

```
GET /admin/stats/overview
```

Returns `{ totalUsers, newUsers30d, activeSessions, organizationCount,
bannedCount, usersWithout2FA, loginChannels }`. `loginChannels` counts linked
accounts by provider: credentials are exposed as `emailPassword`, and every
configured provider ID (for example `google`, `github`, `siwe`, or a custom
OAuth provider ID) is included dynamically.
Counts that depend on an optional plugin (e.g. `organization`) gracefully
return 0 when that plugin is absent. Requires `stats:read`.

### Stats Signups

**Server:** `auth.api.statsSignups({ headers, query: { range } })`

```
GET /admin/stats/signups?range=7d|30d
```

Returns `{ range, data: [{ date, count }] }` — one bucket per day in the window
(pre-seeded with 0 so the chart has no gaps). Requires `stats:read`.

### Stats Security Today

**Server:** `auth.api.statsSecurityToday({ headers })`

```
GET /admin/stats/security-today
```

Returns `{ failedLoginsToday, otpRequestsToday, geoAnomalyCount }` from the
audit log (0 when the audit-log plugin is not installed). Requires `stats:read`.

### List All Sessions

**Server:** `auth.api.listAllSessions({ headers, query })`

```
GET /admin/list-all-sessions?limit=50&offset=0&activeOnly=true&userId=
```

Returns a paginated platform-wide session inventory as
`{ sessions, total, limit, offset }`. Session rows contain the non-secret
database ID, user ID, timestamps, IP address, user agent, and impersonation
metadata; bearer session tokens are never returned. `userId` is optional and
`activeOnly` defaults to `true`. Requires `session:list`.

### Revoke a Session by ID

**Server:** `auth.api.revokeUserSessionById({ headers, body })`

```
POST /admin/revoke-user-session-by-id
body: { sessionId }
```

Revokes a session using its non-secret database ID. The endpoint resolves the
bearer token internally and never exposes it to the caller. Repeating the call
after the session is gone remains successful. Requires `session:revoke`.

### List User Wallets

**Server:** `auth.api.listUserWallets({ headers, query: { userId } })`

```
GET /admin/list-user-wallets?userId=
```

Returns `{ wallets: [{ address, chainId, isPrimary, boundAt, boundIp, boundSite }] }`.
`boundIp`/`boundSite` are enriched from the audit log's `siwe.bind` rows.
Requires `wallet:list`.

### Unbind Wallet

**Server:** `auth.api.unbindWallet({ headers, body })`

```
POST /admin/unbind-wallet
body: { userId, address, chainId }
```

Force-unbinds a SIWE wallet: deletes the `walletAddress` row and the matching
`account` row (best-effort), then writes a `siwe.unbind` audit row. Address
matching is case-insensitive (addresses are stored checksummed). Requires
`wallet:unbind`.

### List a User's Passkeys

**Server:** `auth.api.adminListUserPasskeys({ headers, body })`

```
POST /admin/list-user-passkeys
body: { userId }
```

Returns only non-secret metadata:
`{ passkeys: [{ id, name, deviceType, backedUp, createdAt, aaguid }] }`.
Credential IDs, public keys, counters, and the stored owner ID are never
returned. Requires `passkey:list`.

### Revoke a User's Passkey

**Server:** `auth.api.adminDeleteUserPasskey({ headers, body })`

```
POST /admin/delete-user-passkey
body: { userId, passkeyId }
```

The endpoint verifies that `passkeyId` belongs to the explicit `userId` before
deleting it. Requires `passkey:revoke`.

### Rename a User's Passkey

**Server:** `auth.api.adminUpdateUserPasskey({ headers, body })`

```
POST /admin/update-user-passkey
body: { userId, passkeyId, name }
```

The endpoint verifies the same target-user ownership boundary before updating
the label and returns only non-secret metadata. Requires `passkey:update`.

These Admin endpoints use the adapter's `passkey` model and do not depend on
the `@cinaauth/passkey` package at runtime. A deployment that has not installed
the passkey schema receives the adapter's normal missing-model/table error.
The CinaSeek production Worker requires a fresh authoritative session for
revoke and rename, while listing remains a read-only operation; Admin Console
fulfills that step-up through its OIDC recent-auth proof.

### Wallet address search in list-users

`list-users` now accepts `searchField=wallet` to find users by SIWE wallet
address substring (case-insensitive).

## Access Control

### CinaSeek Admin authentication-method governance

The production CinaSeek Admin console exposes a dedicated **Authentication
Methods** page backed by the Auth Worker's authoritative runtime configuration.
It keeps the status of every sign-in integration visible in one place while
only rendering switches for methods that can safely change without a deploy.

The runtime switches are email verification-code sign-in, email-and-password
sign-in for existing credential accounts, passkey sign-in, SIWE wallet sign-in,
and Google One Tap.

Email/password account creation and password reset remain disabled when the
email/password switch is enabled. New users still enter through verified email
OTP, OAuth, or SIWE. Disabling passkey or SIWE login does not remove existing
credentials and does not disable passkey registration or wallet management in
the account security center.

The page also reports integration-owned capabilities—social and generic OAuth,
SSO, phone OTP, magic links, usernames, and two-factor authentication—and links
to the owning Admin page when one exists. An enabled switch is only effective
when its prerequisite is ready: email OTP requires operational email delivery,
SIWE requires the strict deployment configuration, and One Tap requires an
enabled Google provider with a client ID. The public capability snapshot exposes
that Google client ID because browser-side Google Identity Services needs it;
client secrets are never returned.

Reads require `security.policy.read`. Mutations require
`security.policy.publish`, a recent non-impersonated administrator session, the
exact Admin origin, rate limiting, and intent/outcome audit events. The Worker
rejects a change that would leave no effective runtime method and no visible
OAuth provider, so reducing the social-provider display limit to zero cannot be
used to bypass the last-login-method safeguard.

The browser facade is `GET|PUT /api/admin/authentication-settings`; the
authoritative Worker endpoint is `GET|PUT /api/auth/admin/authentication-settings`.
Runtime settings are stored in the
singleton `cinaauth_sign_in_settings` row and invalidate the five-second sign-in
configuration cache after a successful update.

The admin plugin offers a highly flexible access control system, allowing you to manage user permissions based on their role. You can define custom permission sets to fit your needs.

### Roles

By default, there are three roles:

`admin`: Users with the admin role have full control over other users.

`security_admin`: A scoped admin role for the CinaSeek console. Can list/get
users, ban/unban, manage sessions (revoke), manage SIWE wallets (list/unbind),
list/revoke passkeys, and read stats — but cannot rename passkeys, create or
delete users, set roles, impersonate, set passwords, or edit security policy.
Intended for security operators.

`user`: Users with the user role have no control over other users.

<Callout>
  A user can have multiple roles. Multiple roles are stored as string separated by comma (",").
</Callout>

### Last `super_admin` safeguard

When a custom Admin role map defines the exact `super_admin` role, CinaAuth
prevents `set-role`, `update-user`, and `remove-user` from removing that role
from the final user who holds it. Rejected requests return
`YOU_CANNOT_REMOVE_LAST_SUPER_ADMIN`. The Admin `remove-user` endpoint also
continues to reject deleting the acting administrator with
`YOU_CANNOT_REMOVE_YOURSELF`.

Anonymous identities cannot hold the exact `super_admin` role. Admin
`create-user`, `set-role`, and `update-user` reject attempts to create that
state with `ANONYMOUS_USER_CANNOT_BE_SUPER_ADMIN`. If legacy or direct database
data already contains an anonymous exact `super_admin`, every internal-adapter
deletion path rejects it with
`ANONYMOUS_SUPER_ADMIN_MUST_BE_DEMOTED_BEFORE_DELETION`, even when another
super administrator exists. Demote the identity first, then delete it.

Role membership follows the Admin plugin's established comma-separated
semantics: `user,super_admin` contains the protected role, while
`user, super_admin` does not because role tokens are not trimmed. Removing or
demoting one super administrator remains allowed when another exact
`super_admin` user exists. Deployments using the default `admin`/`user` role
map are unchanged.

The Admin mutation check and write run in one adapter transaction. The plugin
also checks self-service `delete-user`, `delete-user/callback`, and
`delete-anonymous-user` before destructive work, and installs a
`user.delete.before` database hook as the final guard for post-link cleanup,
SCIM, and other internal-adapter deletion paths. CinaAuth now runs that user
preflight before deleting sessions or accounts; a hook veto or read failure
therefore preserves the complete identity rather than leaving a user row that
can no longer sign in. Ordinary-user deletion and user-provided hook ordering
remain unchanged. Because the runtime-agnostic adapter contract does not
expose a portable row or advisory lock, deployments that allow concurrent
super-administrator mutations must still serialize every role-removal and
deletion sink at the deployment boundary.

The included Cloudflare Auth Worker adds two deployment layers. A PostgreSQL
transaction-level queue lock serializes all three Admin mutation routes, both
self-service deletion sinks, anonymous deletion, and SCIM user DELETE. A
versioned PostgreSQL trigger uses a distinct lock key and enforces the final
condition in the same transaction and connection as the actual user write, so
loss of the queue connection cannot release the invariant prematurely.
Session-backed paths are authoritatively authenticated before opening the
queue, and plausible SCIM deletes pass a Durable Object IP-and-route rate limit
before Hyperdrive is opened. Missing authentication storage, rate limiting,
Hyperdrive, the installed trigger, or lock acquisition fails closed. The
deployment trigger targets these single-user API sinks; direct multi-row SQL is
not a supported administrator-management path.

### Permissions

By default, there are two resources with the following permissions.

**user**:
`create` `list` `set-role` `ban` `impersonate` `impersonate-admins` `delete` `set-password` `set-email` `get` `update`

**session**:
`list` `revoke` `delete`

**passkey**:
`list` `revoke` `update`

Users with the admin role have full control over all the resources and actions. Users with the user role have no control over any of those actions.

### Custom Permissions

The plugin provides an easy way to define your own set of permissions for each role.

<Steps>
  <Step>
    #### Create Access Control

    You first need to create an access controller by calling the `createAccessControl` function and passing the statement object. The statement object should have the resource name as the key and the array of actions as the value.

    ```ts title="permissions.ts"
    import { createAccessControl } from "cinaauth/plugins/access";

    /**
     * make sure to use `as const` so typescript can infer the type correctly
     */
    const statement = { // [!code highlight]
        project: ["create", "share", "update", "delete"], // [!code highlight]
    } as const; // [!code highlight]

    const ac = createAccessControl(statement); // [!code highlight]
    ```

    <Callout type="warning">
      To keep bundle sizes small, make sure to import from `cinaauth/plugins/access` instead of `cinaauth/plugins`.
    </Callout>
  </Step>

  <Step>
    #### Create Roles

    Once you have created the access controller you can create roles with the permissions you have defined.

    ```ts title="permissions.ts"
    import { createAccessControl } from "cinaauth/plugins/access";

    export const statement = {
        project: ["create", "share", "update", "delete"], // <-- Permissions available for created roles
    } as const;

    export const ac = createAccessControl(statement);

    export const user = ac.newRole({ // [!code highlight]
        project: ["create"], // [!code highlight]
    }); // [!code highlight]

    export const admin = ac.newRole({ // [!code highlight]
        project: ["create", "update"], // [!code highlight]
    }); // [!code highlight]

    export const myCustomRole = ac.newRole({ // [!code highlight]
        project: ["create", "update", "delete"], // [!code highlight]
        user: ["ban"], // [!code highlight]
    }); // [!code highlight]
    ```

    When you create custom roles for existing roles, the predefined permissions for those roles will be overridden. To add the existing permissions to the custom role, you need to import `defaultStatements` and merge it with your new statement, plus merge the roles' permissions set with the default roles.

    ```ts title="permissions.ts"
    import { createAccessControl } from "cinaauth/plugins/access";
    import { defaultStatements, adminAc } from "cinaauth/plugins/admin/access";

    const statement = {
        ...defaultStatements, // [!code highlight]
        project: ["create", "share", "update", "delete"],
    } as const;

    const ac = createAccessControl(statement);

    const admin = ac.newRole({
        project: ["create", "update"],
        ...adminAc.statements, // [!code highlight]
    });
    ```
  </Step>

  <Step>
    #### Pass Roles to the Plugin

    Once you have created the roles you can pass them to the admin plugin both on the client and the server.

    ```ts title="auth.ts"
    import { CinaAuth } from "cinaauth"
    import { admin as adminPlugin } from "cinaauth/plugins"
    import { ac, admin, user } from "@/auth/permissions"

    export const auth = CinaAuth({
        plugins: [
            adminPlugin({
                ac,
                roles: {
                    admin,
                    user,
                    myCustomRole
                }
            }),
        ],
    });
    ```

    You also need to pass the access controller and the roles to the client plugin.

    ```ts title="auth-client.ts"
    import { createAuthClient } from "cinaauth/client"
    import { adminClient } from "cinaauth/client/plugins"
    import { ac, admin, user, myCustomRole } from "@/auth/permissions"

    export const client = createAuthClient({
        plugins: [
            adminClient({
                ac,
                roles: {
                    admin,
                    user,
                    myCustomRole
                }
            })
        ]
    })
    ```
  </Step>
</Steps>

### Access Control Usage

**Has Permission**:

To check a user's permissions, you can use the `hasPermission` function provided by the client.

<APIMethod path="/admin/has-permission" method="POST">
  ```ts
  type userHasPermission = {
      /**
       * The user id which you want to check the permissions for. 
       */
      userId?: string = "user-id"
      /**
       * Check role permissions.
       * @serverOnly
       */
      role?: string = "admin"
      /**
       * Optionally check if a single permission is granted. Must use this, or permissions. 
       */
      permission?: Record<string, string[]> = { "project": ["create", "update"] } /* Must use this, or permissions */,
      /**
       * Optionally check if multiple permissions are granted. Must use this, or permission. 
       */
      permissions?: Record<string, string[]>
  }
  ```
</APIMethod>

Example usage:

```ts
import { authClient } from "@/lib/auth-client";

const canCreateProject = await authClient.admin.hasPermission({
  permissions: {
    project: ["create"],
  },
});

// You can also check multiple resource permissions at the same time
const canCreateProjectAndCreateSale = await authClient.admin.hasPermission({
  permissions: {
    project: ["create"],
    sale: ["create"]
  },
});
```

If you want to check a user's permissions server-side, you can use the `userHasPermission` action provided by the `api` to check the user's permissions.

```ts title="permission.ts"
import { auth } from "@/lib/auth"

await auth.api.userHasPermission({
  body: {
    userId: 'id', //the user id
    permissions: {
      project: ["create"], // This must match the structure in your access control
    },
  },
});

// You can also just pass the role directly
await auth.api.userHasPermission({
  body: {
   role: "admin",
    permissions: {
      project: ["create"], // This must match the structure in your access control
    },
  },
});

// You can also check multiple resource permissions at the same time
await auth.api.userHasPermission({
  body: {
   role: "admin",
    permissions: {
      project: ["create"], // This must match the structure in your access control
      sale: ["create"]
    },
  },
});
```

**Check Role Permission**:

Use the `checkRolePermission` function on the client side to verify whether a given **role** has a specific **permission**. This is helpful after defining roles and their permissions, as it allows you to perform permission checks without needing to contact the server.

Note that this function does **not** check the permissions of the currently logged-in user directly. Instead, it checks what permissions are assigned to a specified role. The function is synchronous, so you don't need to use `await` when calling it.

```ts
import { authClient } from "@/lib/auth-client";

const canCreateProject = authClient.admin.checkRolePermission({
  permissions: {
    user: ["delete"],
  },
  role: "admin",
});

// You can also check multiple resource permissions at the same time
const canDeleteUserAndRevokeSession = authClient.admin.checkRolePermission({
  permissions: {
    user: ["delete"],
    session: ["revoke"]
  },
  role: "admin",
});
```

### Email Enumeration Protection

If you use [email enumeration protection](/docs/authentication/email-password#email-enumeration-protection) (`requireEmailVerification` or `autoSignIn: false`), you need to configure `customSyntheticUser` to include the admin plugin fields in the fake sign-up response:

```ts title="auth.ts"
export const auth = CinaAuth({
  emailAndPassword: {
    enabled: true,
    requireEmailVerification: true,
    customSyntheticUser: ({ coreFields, additionalFields, id }) => ({
      ...coreFields,
      // Admin plugin fields (in schema order)
      role: "user", // or your configured defaultRole
      banned: false,
      banReason: null,
      banExpires: null,
      ...additionalFields,
      id,
    }),
  },
  plugins: [admin()],
});
```

## Options

### Default Role

The default role for a user. Defaults to `user`.

```ts title="auth.ts"
admin({
  defaultRole: "regular",
});
```

### Admin Roles

Specifies which roles are considered admin roles. Defaults to `["admin"]`. Custom roles (for example, `superadmin`) must be defined in custom access control.

```ts title="auth.ts"
admin({
  // Requires custom access control with `superadmin` defined in `roles`
  adminRoles: ["admin", "superadmin"],
});
```

<Callout type="warning">
  **Note:** The `adminRoles` option is **not required** when using custom access control (via `ac` and `roles`). When you define custom roles with specific permissions, those roles will have exactly the permissions you grant them through the access control system.

  **Warning:** When **not** using custom access control, only `admin` and `user` exist as valid roles. Any role that isn't in the `adminRoles` list will **not** be able to perform admin operations.
</Callout>

### Admin userIds

You can pass an array of userIds that should be considered as admin. Default to `[]`

```ts title="auth.ts"
admin({
    adminUserIds: ["user_id_1", "user_id_2"]
})
```

If a user is in the `adminUserIds` list, they will be able to perform any admin operation.

### impersonationSessionDuration

The duration of the impersonation session in seconds. Defaults to 1 hour.

```ts title="auth.ts"
admin({
  impersonationSessionDuration: 60 * 60 * 24, // 1 day
});
```

### Default Ban Reason

The default ban reason for a user created by the admin. Defaults to `No reason`.

```ts title="auth.ts"
admin({
  defaultBanReason: "Spamming",
});
```

### Default Ban Expires In

The default ban expires in for a user created by the admin in seconds. Defaults to `undefined` (meaning the ban never expires).

```ts title="auth.ts"
admin({
  defaultBanExpiresIn: 60 * 60 * 24, // 1 day
});
```

### bannedUserMessage

The message to show when a banned user tries to sign in. Defaults to "You have been banned from this application. Please contact support if you believe this is an error."

```ts title="auth.ts"
admin({
  bannedUserMessage: "Custom banned user message",
});
```
